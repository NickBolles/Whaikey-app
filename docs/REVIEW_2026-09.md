## 0. Executive summary

**The state of the codebase.** Whaikey is much further along than its own plan describes, and further along in a different direction. The core loop (search → bottle → own/tried/wishlist → pour with rating, nose/palate/finish and wheel tags → journal) is live and solid. So are label and barcode scanning with an async queue, an AI concierge with seven tools, note extraction, pairings, explained recommendations, social phases S1–S2 and most of S3 (profiles, follows, blocks, per-pour visibility, Same Dram, cheers, comments, reports, taste twins, phone/QR discovery, one-tap privacy reset), a passport with tiered badges, a Whiskey School with quizzes, and a nine-source catalog pipeline with verification. The engineering quality is high: no IDOR found across 40+ routes, visibility enforced with live SQL predicates, atomic DB-backed rate limits, zero `@ts-ignore`, zero TODOs, a thorough CI pipeline, and comments that carry real design rationale.

**Why it feels clunky.** Not because screens are unfinished. Each screen is well crafted. It is clunky because:
1. **Every primary action is below the fold.** Home is 2,589 px, the bottle page 3,064 px, the pour form ~1,800 px on a 390×844 viewport. The rating on the pour form is the seventh element in the DOM; "I own it" on the bottle page is at ~2,500 px; the first bottle on My Bar is at ~1,050 px, under a flavor wheel and a 15-chip legend.
2. **The nav does not match the five verbs.** Friends and Chat hold two of five slots and are the two thinnest surfaces (a one-person Friends tab; a Chat tab that can render a developer setup card). Explore, Learn, Search and the Journal have no home.
3. **There is no way back, no edit, no delete, no settings, no sign-out.** Non-tab routes have no back affordance, iOS swipe-back is not enabled, `DELETE /api/pours/[id]` is reachable from no UI, and `signOut` is called from zero components.
4. **The same job is drawn several ways.** Three search UIs, six bottle-row anatomies, two sharing controls on every journal row, four ways to add a bottle, three ways to claim a handle.

The three screens that already work (Learn hub, Compare, Note discussion) are one screen, one action, one payoff. STORYBOARD.md makes that the target for everything else.

## 2. Security

**Method.** Every handler under `src/app/api/**` was read end to end, together with the libraries behind them (`src/lib/session.ts`, `auth.ts`, `native-auth.ts`, `social.ts`, `pour-sharing.ts`, `phone.ts`, `ai/*`, `scan.ts`, `import.ts`, `ingest/*`), the pages that render cross-user data, `next.config.ts`, the native platform config, CI workflows, and a sweep for sinks (raw SQL, `dangerouslySetInnerHTML`, `child_process`, `fetch`, committed secrets).

**Headline.** The authorization model is unusually well built: every route is behind `requireUser()`, every `[id]` route re-checks ownership inside the SQL predicate, and the social visibility model is enforced with live SQL predicates rather than snapshot lists. The real weaknesses are concentrated in the **native device-code sign-in flow**, in **missing HTTP security headers**, and in a handful of **aggregate and enumeration leaks** just outside the guarded read paths. No Critical findings.

### High

**SEC-H1 · Native auth code has no state/PKCE binding; the app auto-redeems any inbound code (session fixation and hijack).**
Files: `src/app/api/auth/native/complete/route.ts:17-61`, `src/components/native-shell.tsx:54-72`, `src/app/api/auth/native/exchange/route.ts:20-55`, `src/lib/native/auth.ts:35-58`, `android/app/src/main/AndroidManifest.xml:30-36`, `ios/App/App/Info.plist` (`CFBundleURLSchemes: whaikey`).
- `/api/auth/native/complete` is a GET that mints a session-equivalent bearer code for whoever holds the browser session and 302s it into `whaikey://auth/callback?code=…`. No `state`, no PKCE, no check that a native `/start` ever happened. SameSite=Lax lets a cross-site top-level navigation carry the cookie.
- `whaikey://` is an unverifiable custom scheme. On Android any app can register it; on iOS the last installer wins. A malicious app receives the victim's code.
- `native-shell.tsx:58-62` redeems any inbound `whaikey://auth/callback?code=…` with `window.location.assign(exchangeUrl(...))` with no user interaction and no origin check. An attacker who pushes their own code at a victim's app silently swaps the victim's WebView into the attacker's account, so every pour and note the victim logs afterwards lands in the attacker's account.
- `src/lib/native-auth.ts:116-121` ships a `safeEqual` helper documented as "kept here for the state parameter checks". It has zero call sites.
Remedy:
1. Add PKCE: `/start` accepts an S256 `code_challenge` generated by the app and stores it on a pending-auth row; `/complete` carries the pending id through `callbackURL`; `/exchange` requires `code_verifier` and compares `sha256(verifier)` with the stored challenge via `safeEqual` before redeeming. Reject codes minted without a challenge.
2. Add a `state` nonce generated in `startNativeSignIn`, stored via Capacitor Preferences, echoed in the callback and compared in `native-shell.tsx` before calling `exchangeUrl`. Drop mismatches.
3. Use the already-verified Universal/App Links (`https://<host>/auth/callback`) for the auth callback; keep `whaikey://` only as a state-gated fallback.
4. Make `/api/auth/native/complete` refuse requests without a valid pending-auth id.
**Status: 1, 2 and 4 fixed (WP-2); 3 blocked on a decision.**
- PKCE: `/start` now requires an S256 `code_challenge` and a `state`, both minted in `startNativeSignIn` and parked on a new `native_auth_requests` row; `/complete` carries only that row's id through `callbackURL`; `/exchange` requires `code_verifier` and compares `sha256(verifier)` to the stored challenge with `safeEqual`, which now has a call site (SEC-L6 closed with it). A code with no challenge is never redeemable. A wrong verifier destroys the code, so an interceptor gets one attempt rather than a search.
- State: minted with the verifier, held in Capacitor Preferences, and compared in `native-shell.tsx` before anything is redeemed — read without consuming, and cleared only on a match, so a forged callback can't cancel a real sign-in by taking the verifier with it. A callback with a missing or wrong state — which is all an attacker who never saw the nonce can produce — is dropped silently, because there is no user to warn about a link nobody asked for.
- `/complete` mints nothing without a live, unconsumed request id, and consumes it whatever the outcome. `/start` takes no credentials by necessity, so live pending rows are capped (`MAX_LIVE_AUTH_REQUESTS`, oldest pruned) — expiry alone bounds nothing against a burst inside the TTL. A proper per-IP throttle needs a store keyed by something other than a user row; that belongs with SEC-M3 in WP-25. An **expired** request is distinguished from an unknown one and gets its state echoed back, because the app drops any callback it cannot match — a stateless answer to a slow-but-real OAuth round trip left sign-in hanging on "Connecting…" until the user restarted. An id nobody issued still gets nothing, which is the forged case. The `next` path is parked on the row rather than the URL, so the round trip can't rewrite where sign-in lands.
- **NOT DONE, and load-bearing: Universal/App Links for the callback (remedy 3).** An earlier version of this note called it "defence in depth". That was wrong, and the correction matters more than the rest of this status line.

  PKCE defeats an app that *intercepts* the callback. It does nothing against an app that **initiates** the flow: a malicious app that has also registered `whaikey://` can open `/api/auth/native/start` with a challenge and state of its own, let the victim complete a genuine Google sign-in in the system browser, receive the callback, and redeem the code with the verifier it chose. The pending row proves `/start` was called, not that *Whaikey* called it, and state proves the callback matches the initiator — who is the attacker. The result is the victim's session in the attacker's hands. This is exactly why RFC 8252 requires a claimed `https` redirect rather than a custom scheme, and it is the residual half of SEC-H1.

  Blocked, not deferred by choice: iOS needs an Associated Domains entitlement and an `apple-app-site-association`, Android's already-declared `autoVerify` App Link needs `/.well-known/assetlinks.json` with a signing fingerprint, and all of it names a team id, bundle id and domain that do not exist until §7 Lane E decision 4 is made. **Native sign-in should not ship to either store until the callback is a verified App/Universal Link** — that is a launch gate, tracked with WP-20, not a nice-to-have. What this PR did close: interception (PKCE), the unsolicited-callback account swap (state), and `/complete` minting for anyone with a browser session (the pending row).

**SEC-H2 · Raw signed session cookies stored in plaintext and never deleted after redemption.**
Files: `src/lib/native-auth.ts:43-69` (issue), `:84-109` (redeem), `src/db/schema.ts:1024-1040`.
`nativeAuthCodes.sessionCookie` holds the verbatim Better Auth signed session cookie, a weeks-long credential, in cleartext. Redemption only sets `usedAt`; rows are never deleted. Cleanup runs opportunistically inside `issueNativeAuthCode`, so with no native sign-ins for a week every credential minted in that window sits readable. Any DB read access (leaked pooler URL, backup, replica, the `catalog-production` environment's `DATABASE_URL` on a self-hosted runner) yields directly replayable sessions.
Remedy: make redemption `DELETE … WHERE code_hash = ? AND used_at IS NULL AND expires_at > now() RETURNING` (atomic, keeps the exactly-once property, destroys the secret). Sweep rows older than `2 × CODE_TTL_MS` on redeem and on a schedule, not only on issue. Encrypt `sessionCookie` at rest (AES-GCM keyed from `BETTER_AUTH_SECRET`) if any audit trail is kept.

## 3. Correctness and reliability

Findings are ranked P0–P3. Each was read in source. Two are marked *needs verification* where the local stack (PGlite) cannot reproduce production (postgres-js) behaviour.

### 3.1 Offline and native

**REL-4.1 · P0 · Web/PWA offline pours are acknowledged and never sent.**
`src/app/pour/pour-flow.tsx:358-362` enqueues on any `TypeError` regardless of platform and shows "Saved on your phone — it'll sync when you're back online" (`:390`). The only caller of `flushPourQueue` is `src/components/native-shell.tsx:30`, inside an effect that returns early when `!isNativeApp()` (`:35`). A browser/PWA user's pour sits in `localStorage` (`whaikey.pour-queue.v1`) forever, unretried and unsurfaced. `offline-queue.ts:11` claims the web "gets the same behaviour". Silent data loss with a false reassurance on the core loop.
Fix: mount an always-on effect (root layout, before the native guard) that runs `syncQueue()` on mount and on `window` `online`; add a test asserting a flush with `isNativeApp()` false.
**Status: fixed (WP-1).** `NativeShell` now has two effects — one for the native plugin wiring, one for the pour flush that runs on every platform, on mount, on `online`, and on `visibilitychange`. `src/components/native-shell.test.tsx` asserts the flush with no `window.Capacitor`. Queue entries carry their author, because web storage is per **origin** and not per session: switching the flush on made it possible for a pour queued by one person to be sent while someone else is signed in on the same browser, so an entry whose owner isn't the current user is skipped and left in place — skipped rather than stopped at, since halting there would strand the signed-in user's own later pours behind it forever, and no timeline spans two accounts. Entries queued by earlier releases carry no author at all and are **held, not guessed at**: sending them as whoever is signed in is right on a single-account device and writes a private tasting note into a stranger's journal on a shared one, and private-by-default is not a probability. `FlushResult.unclaimed` counts them so a surface can offer them back to their author. The binding is enforced **server-side** as well: a pour states the author the client believes it is writing as (`expectedUserId`) and `POST /api/pours` refuses with 409 when that isn't the session — client-side selection cannot close the race where the account changes part-way through a multi-entry flush, since `fetch` carries whatever cookie is current, and the queue holds a 409'd entry rather than spending an attempt on it. Queue writes take a **Web Locks** lock, not just an in-process promise chain: a chain is per-document, and two tabs of the PWA is the ordinary case on the web — precisely where this flush was switched on. A pour the server keeps rejecting is likewise **quarantined rather than deleted** (`readQuarantine()`): an automatic background retry, which now runs unprompted on every platform, must never be the thing that destroys writing the user was told was saved.
**Remaining (needs UI, and the reason this is not wholly closed):** nothing yet *shows* either state. Until a surface exists — WP-6's toast is the natural home — a quarantined or unclaimed pour is retained, logged, and invisible, so "Saved on your phone" is still not fully honest for those two cases.

**REL-4.2 · P1 · Queued pours have no idempotency key.**
`src/lib/native/offline-queue.ts:20-27` documents it: a flush whose response is lost stays queued and double-logs, which also double-decrements `fillLevel` (`src/lib/pours.ts:176-180`) and skews the palate.
Fix: add `clientId: z.string().uuid().optional()` to `pourInputSchema` (`src/lib/pours.ts:40`), store it on `pours` with `uniqueIndex(userId, clientId)`, return the existing row on conflict; `enqueuePour` already mints an id at `:99`.
**Status: fixed (WP-1).** `pours.client_id` + `uniqueIndex(user_id, client_id)` (migration `0022`); `logPour` takes a per-user advisory lock on the key, returns the existing pour and its note on a replay, and writes nothing. Entries queued by earlier releases carry no key, and are stamped at flush time with the queue id they already have — they are the ones that have waited longest, so their first flush is also the first chance to double-log them. The key is a free-form string rather than a UUID so the queue's own non-crypto id fallback (an offline WebView has no secure context) is usable. `pour-flow.tsx` mints it once per pour and reuses it across retries, which is what makes a lost 201 harmless.

**REL-4.3 · P1 · Concurrent flushes duplicate and clobber.**
`offline-queue.ts:134-190` is read → network → write with no in-flight guard; `syncQueue` is invoked from mount, `online` and `onResume` (`native-shell.tsx:82,87,89`), which fire within milliseconds on resume. **Status: fixed (WP-1).** `flushPourQueue` is single-flight and hands every caller the same result; the write-back re-reads storage under a serializing lock and removes only the ids this flush settled, so a pour logged mid-flush survives.

**REL-4.4 · P3 · `enablePush` leaks listeners and never retries registration** (`src/lib/native/push.ts:55-60,79-89`). `removeAllListeners()` before adding; retry `storeToken` from `onResume`.

### 3.3 AI layer

**REL-3.1 · P1 · No timeout or retry budget on model calls.** `src/lib/ai/client.ts:70` uses SDK defaults (10 min, 2 retries). **Status: fixed (WP-5)**, bar the reservation release. 25 s per call and **no** retry — deliberately not the fix line's `maxRetries: 1`, because the budget the platform enforces is wall time across every attempt: a second 25 s attempt starting at 25 s is killed by a 30 s `maxDuration` and reproduces exactly the 504-on-a-spent-reservation this is meant to prevent. A retry is worth having with a per-route budget to fit it in, which belongs with WP-25. Two budgets sit on top of that: the chat tool loop shares one 50 s budget across its up-to-seven calls and hands each what is left (a per-call timeout bounds nothing when the caller loops), and batch work off a route — `pnpm ingest enrich`, catalog sync — gets its own five-minute budget, because those answer to a job runner rather than a platform deadline and are slow on purpose. **Status (WP-16).** Built as specified, plus three things the fix line didn't name and the code needed:

- **The visibility rule is a `WHERE` fragment, not a post-filter.** `catalogVisibleTo(userId)` (`src/lib/catalog-visibility.ts`) is pushed into every catalog read — search, browse, bottle detail, the discovery recommender, the concierge's `search_bottles`/`get_bottle_details`/`get_pairings`, label-scan candidates, import matching, shelf adds and `logPour`. Filtering the rows afterwards would silently change what each query's `LIMIT` means.
- **A submission does not teach the scanner.** A `bottle_upcs` row is crowdsourced truth every other scanner resolves against, so a barcode that arrives with a submission is parked on the submission row and published (`publishSubmissionUpc`) when the bottle is promoted. Same for an imported row's barcode.
- **User input never creates a distillery.** A typed distillery is linked on an exact (case-insensitive) name match and otherwise parked as `distilleryText` for the reviewer — a second uncurated catalog would just move the problem.
- **A pour of a pending bottle is private, whatever was asked for.** The friend feed, a shared note and a profile's recent notes all join the bottle for its name and none of them checks its status, so a public pour of a pending bottle would publish the bottle through the side door. Held down at write time rather than filtered on read: one place instead of every social projection, and it fails closed. Promotion does not raise it — the system never raises a visibility, and its owner can publish the note themselves.
- **The dedupe prompt is inside the write's lock.** Two identical requests could both clear a check made before the transaction and then insert one after the other; the prompt has to be the same critical section as the insert or it is only a prompt most of the time.
- **The scanner adds in its own sheet.** `/scan` is a batch tool whose queue lives in component state, so a link out to `/bottles/new` would discard every other scan in flight. Same route underneath, same dedupe prompt, no navigation.

One thing the work turned up that wasn't in the finding: **the passport counted a bottle you added yourself.** `catalogTotals` filtered its denominator to `status = "verified"`, but `listMetBottles` (and the badge drill-down) had no status filter at all, so owning or pouring a self-submitted bottle minted country/region/style progress — "have I been to Campbeltown?" answered by typing, and a stamp that could pass its own total. Both numerator queries now exclude `user_submitted`. This is the guardrail in AGENTS.md read the other way round: the test is whether someone can win by drinking less of more, and the answer here was that they could win without drinking at all.

One deliberate limit at the time: the review queue had rows but **no operator UI**, so a submission stayed private to its submitter indefinitely. ✅ **Closed by WP-18** — `/admin/submissions` promotes, declines or marks a duplicate, and the submitter reads the outcome on the bottle's own page. The copy still says "once someone has checked it over" rather than promising a date, because with one operator that is still the honest version.

**Status (WP-17).** A date of birth and a market, asked once, at `/age`; `/responsible` is the resources page. Three things worth naming:

A gate applied per-screen is a gate somebody forgets on the one screen that mattered. The test seam enforces it too: `mockSessionModule`'s `requireUser` reads the real gate state from the test database, so a route test cannot pass against a gate the app would have closed.

**Status (WP-18).** A queue, a role, two policy pages, a support page and a feedback box — plus the correction to the store document that started this work package.

- **The operator role is an env allowlist, and an empty one grants nobody.** `WHAIKEY_OPERATOR_IDS` (`src/lib/operator.ts`), user ids rather than emails, because an email is a claim the identity provider can change and every other table already keys on the id. A deploy that forgets the variable gets a queue nobody can open, which is the failure worth having; the alternative failure is a role column that drifts. It becomes a real role when there is a second operator and a reason to grant access without a deploy.
- **A non-operator gets 404, not 403.** Both `/admin/reports` and `POST /api/admin/moderation` answer as if the surface does not exist. 403 tells an attacker the path is real and that there is a list to get onto; there is nothing here a would-be operator needs to be told.
- **Moderation is append-only.** `moderation_actions` records actor, action, subject, report and a reason for every hide, suspend, reinstate and dismiss. The report row moves to resolved; the history does not move at all. An audit trail you can edit is a log, not a trail — and Apple's UGC requirement is specifically that action is *evidenced*, not that it happened.
- **Every rule in here needed its doors counted, and review found four that were open.** Hiding a pour made it private and left its `/s/` bearer links live, because `getPublicPourShare` authorises on `revokedAt` alone — so the operator hid the content and anyone with the URL kept reading it. **Suspending an account had exactly the same hole and the second review pass found it**: the profile flags went off and the links stayed live, which is being suspended from the surfaces nobody was reading. Suspension now applies the whole account-wide reset under the `social-reset:` lock. And hiding a pour was undoable by its author in one PATCH, because a hide uses the owner's own visibility field — the profile version of this was answered by removing the action, and here by closing the door: the audit trail is the authority on whether a hide stands, an operator's `unhide` lifts it, and lifting hands back control rather than visibility. Suspending cleared three exposure flags and not `phoneDiscoverable`, handing the account that exposure back on reinstatement without ever asking. Suspending resolved the report, which took the row out of the queue along with the only Reinstate button, so an appeal arriving later had nowhere to land. And the suspension reason was stored where its subject could not read it, while the Terms and `/support` both said they had been told. All four are the same shape as WP-20's push-token finding: the rule was right and the thing around it wasn't. Later passes found the same shape three more times — a hidden pour could be re-shared at a fresh `/s/` code because revoking existing links left the mint open; the hide check could straddle the hide itself without a lock both sides take; and lifting a comment hide would have republished a comment its author had deleted seconds before the hide landed, because `applyHide` counts an already-deleted row as success. Each is one more door on a rule that was already correct.
- **A report has to carry what it is about.** The queue rendered the subject's *current* text, so a reported user who edited the comment before an operator opened the report left them judging content nobody had objected to — and rewriting the abuse was a complete defence. `reports.subject_snapshot` captures the subject at the moment the report is filed, inside the same transaction, so a subject edited between the read and the insert cannot be recorded as the original. The queue leads with the snapshot and shows the current version only when the two differ, under an "Edited since it was reported" flag: the operator needs both, and the one they judge against is the reported one. Rows filed before snapshots existed have none, and the queue says so instead of passing today's text off as the original — an unknown is not a difference, and flagging every old row "edited" would train the operator to ignore the flag that matters. One `subjectPreview` serves both the snapshot and the live view, because two projections of the same thing are how they drift.
- **The queue was showing the operator what was never shared.** The "Now" projection read the subject's current text by id, with no visibility check — so an author who made their pour private, or switched social off, and *then* edited had that revision rendered to the operator. Nobody could ever have seen it and no complaint was about it, and `docs/STORYBOARD.md` §3.17 is binding on exactly this: "An operator can hide a thing and suspend an account; they cannot read what was never shared." The snapshot is unaffected — the reporter saw it and it is what the decision is judged on — but the live projection is now gated on the same conditions that made the subject reportable, rather than on the operator's privileges, which are for acting and not for reading. Where it is withheld the queue says *why* ("deleted, made private, or its author stepped back"), because "gone" and "no longer yours to read" call for different readings of the same report, and the row is **not** flagged edited — an unknown is not a difference.
- **A guard on future writes leaves the rows already written.** Three findings in one pass, all the same shape, and all against fixes from the two passes before it. Refusing a non-private visibility from a profile-less account does nothing about the `public`/`friends`/`followers` pours earlier releases stored: those are invisible only because `canViewPourContext` reads `authorSocialEnabled ?? false`, and **claiming a handle is exactly what flips that** — so a first handle would have published an entire back catalogue of notes at once, with nobody choosing it. `createProfile` now clamps them private in the same transaction as the insert. Clamped there rather than backfilled by a migration because that is the only moment the exposure can occur: before the profile the rows are unreadable, and after it nothing can write another one. Likewise `addComment` refusing a profile-less commenter left the comments already written, still visible, still reportable, and still attached to an account `suspendAccount` throws on — so `commentWithdrawnByAuthor` treats a **missing** profile as withdrawn rather than as enabled (`!== true`, not `=== false`), which is the same answer `logPour` and `updatePourVisibility` already give. The lesson is worth more than the three fixes: **a rule newly enforced on writes is a claim about the past that has to be checked**, and the place to check it is wherever the old data first becomes visible.
- **And the effective-date fix contradicted two binding documents.** Making the date part of completeness left `docs/STORYBOARD.md`, `PLAN.md` §9.3 and `.env.example` all still describing three facts and an optional fourth — and left the banner asserting that the entity, jurisdiction and address were unnamed on a page that names them. A notice that is wrong about three quarters of its own subject is how a reader learns to stop believing it, and this notice *is* the store-readiness check. The banner now lists only what is actually absent, and all three documents say four.
- **Making the account deletable stranded what it had submitted.** `bottles.submitted_by` was `no action`, so a single submission made an account permanently undeletable; `set null` fixed that and created a second problem in the same move. `bottle_submissions.submitted_by` cascades, so deleting an account leaves an unapproved bottle with a null submitter and no submission row — and `catalogVisibleTo` shows a `user_submitted` bottle **only** to its submitter, so it is visible to nobody, reviewable by nobody, and permanent. User-entered content outliving the account it belongs to, under a Privacy Policy that promises deletion. Closed at the source rather than by teaching moderation to cope: content that should not exist is better prevented than moderated. The alternative — moving suspension off the profile row — is the answer if some later path does reach that state, and is recorded here rather than built, because nothing reaches it today.
- **Two doors stored a visibility that was not in force.** `logPour` and `updatePourVisibility` both let an account with no profile set `public`, which `canViewPourContext` then showed to nobody — and creating a profile later would have published those pours retroactively, with no fresh decision. That is precisely what the US-11 rule sitting in `logPour` already refuses to do for a *stepped-back* user; a missing profile is the same answer as social switched off, and now gets it. `updatePourVisibility` also answers a missing or foreign pour with `null` **before** any social check, so "not found" cannot come back as "social is turned off" — wrong, and a small oracle about somebody else's row. **This has a UI consequence worth naming:** handles are claimed lazily "at first social action, never at signup" (`createProfile`), and publishing a pour now *is* one of those actions — so the app has to prompt for a handle where it previously accepted the write and quietly did nothing. That prompt is Lane B's settings work; until it exists the API answers with `SocialDisabledError` rather than storing a visibility that never takes effect. Three tests failed on this and every one of them was incidental — their users had no profile because nothing had ever required one, and each test's stated subject was the pending-bottle rule or ownership, not social opt-in.
- **A protection that a stale tab can omit is not a protection.** The suspend-also-hides fix above first took the subject as two *optional* body fields, so a queue tab loaded before they existed would send `reportId` alone and the content would quietly stay up — with the failure invisible, because the report still resolves and the row still disappears. The subject is read from the report row server-side now, which also means a request cannot name a different subject to hide than the one it is answering for. The automatic hide is linked to that report too: an append-only trail that cannot say which complaint caused a takedown answers an appeal with half the story.
- **And the audience test had to be about the comment's author, not only its pour.** `listComments` skips a comment for any viewer blocked either way with **its author**, and `blockUser` only deletes follow edges between the blocking pair — so a comment whose author has blocked every friend of the pour owner is readable by nobody while the pour itself is still shared. Writing that test found two modelling errors of my own: the audience has to **exclude the comment's author** (reading your own comment is not it being shared — the distinction this whole gate turns on) and **include the pour's owner**, who is in no follow set but reads every comment on their own pour.
- **The gate stopped at the visibility *string*, and the tier can be empty.** `canViewPourContext` does not treat "friends" or "followers" as shared on the strength of the column — it requires a mutual friendship or an accepted follow. A friends-only pour whose owner's last friendship has gone is shared with nobody, so its post-report revision was still being rendered under "Now". The gate now asks whether the tier has anybody in it, as two set queries over `follows` for the whole page rather than a count per row. Blocks need no separate handling because `blockUser` deletes the follow edges in both directions, so a blocked pair is already not an audience.
- **Hide and Suspend were mutually exclusive per report, and that made suspension leak.** Whichever the operator clicked resolved the report and took the row with it — and the row was the only place the reported subject's id appeared. So "suspend the author" left the reported comment in place, hidden only by the author's suspended `socialEnabled`; a reinstatement plus their own re-enable published it again, because `listComments` reads that flag and nothing had recorded a hide. A suspension is not a takedown. Suspending from a comment or pour report now hides that subject **in the same transaction**, so the account action and the content action commit together or not at all, and the hide outlives the reinstatement the way every other hide does. It also runs on the already-suspended path, because a second report about one account is usually about a different comment.
- **And a fourth door on the same rule: a deleted comment.** `listComments` returns `body: null` for a tombstone — to *everybody*, its author included — so a soft-deleted comment is text nobody can read. `createReport` still accepted its id and captured `comments.body` as the snapshot, which is how a stale caller reporting after an edit and a delete would have put a revision they never saw in front of the operator. Refused now, and kept as its own clause rather than folded into the withdrawn-author predicate, because this one applies to the author too. There is also nothing lost by refusing: the content is gone, so there is nothing to hide, and an account that needs answering for is reportable through its profile.
- **Then the same rule was missing a third time, on the *creation* path — so the fix was to stop writing it again.** `listComments` drops a stepped-back author's comments for everyone but themself (US-11), and `createReport`'s comment branch checked the parent pour and the block relationship but not that: a caller holding a stale comment id could report a comment the app had stopped showing them, and the snapshot preserved its current body — possibly a revision written *after* the step-back — into the queue as report-time evidence. Three incomplete copies of one rule is a structural answer rather than a third patch, so the predicate is now a pure function both call. It has to be a pure predicate rather than a shared query: `listComments` applies it per row inside a bulk read and `createReport` applies it to one comment, so either calling the other reintroduces an N+1 or a cycle. **This is the pattern of the whole lane's last four findings** — the rule was right and something beside it was not — and the cause each time was a second implementation written from memory of the first.
- **And the first version of that gate re-implemented the visibility rule instead of matching it.** It checked a reported comment's *author* `socialEnabled` and its pour's visibility tier, but never the **pour owner's** switch — which is what `canViewPourContext` tests first, before it looks at the tier at all. So a comment under a pour whose owner had stepped back stayed readable, and a revision written afterwards was still rendered. The gate deliberately does not delegate to `canViewPourContext` (that asks "may *this viewer* see it", and half its answer is friends-and-followers relative to a viewer the queue does not have; this asks "is it still shared with anyone at all") — but it has to stay **at least as strict** on the parts that are not viewer-relative, and it was not. This is SEC-M2's lesson recurring: two implementations of one rule is how the filter ends up on one and not the other, and writing a second one is a decision that has to be justified and then checked against the first, clause by clause.
- **A page built from several queries is several states unless it is one snapshot.** `listSuspendedAccounts` read the profile row and the standing action separately, so a reinstatement of A followed by a suspension of B landing between them produced a row showing **A's** reason and timestamp with **B's** action id — which passes the reinstatement guard, so the operator would have lifted a decision they never reviewed using the guard built to prevent that. Both list functions now read inside a read-only **repeatable read** transaction. Nothing blocks ahead of their first query, which is what makes that safe here and did not in `createReport`.
- **A standing hide is proof the subject existed.** The idempotent hide branch still ran an existence check, so once the owner deleted a hidden pour — `deletePour` is a hard delete — every remaining report about it was stranded: the queue offered "Resolve as hidden" because the hide genuinely stands, and the click threw. Those reports could then only be closed by dismissing real complaints as unfounded. The check is gone from that branch only; a *first* hide on something that was never there is still refused. The report is still claimed against its own subject, because `resolveOpenReport` reads the report row rather than the subject.
- **A guard is only as good as the lock the decision it names is read under.** Suspension held `social-reset` and reinstatement held `moderation:profile`, so the two paths did not exclude each other and the action-id guard above bought nothing on its own: a stale reinstatement could validate suspension A, let B commit, and then clear B — the decision-nobody-reviewed the guard exists to refuse, one layer down. `suspendAccount` now takes both, `social-reset` first because that is the global order and reversing it is the ABBA deadlock.
- **A suspension over a suspension records nothing, exactly as a hide over a hide does.** Several open reports about one account is the ordinary case, and applying a second suspension overwrote `suspendedAt` and `suspendedReason` with a decision nobody asked for — losing the reason the account had been *told* and leaving two rival `suspend` rows describing one state. The queue also hid Suspend once an account was suspended, so a later profile report could only be closed by dismissing a real complaint or by *reinstating* the account to resolve a report that agreed with the sanction. The control now reads "Resolve as suspended" and the backend absorbs it. Third instance of one shape: the ordinary case is several reports about one thing, and every action needs an idempotent form that resolves the later ones.
- **"Inside one transaction" was not the guarantee it sounded like — and the obvious fix broke the rate limiter.** Read committed takes a fresh snapshot per *statement*, so grouping the visibility check and the content read into `createReport`'s transaction narrowed the edit window without closing it. Raising the whole transaction to **repeatable read** closed that and immediately opened something worse: at repeatable read the snapshot is fixed by the first *query*, and the first query was the blocking `pg_advisory_xact_lock` — so every waiter pinned a view from **before** the lock holder inserted, the duplicate check and the hourly count went blind to it, and concurrent reports from one reporter would all have been admitted. That is the flood control SOCIAL §11 requires, defeated by the fix for a smaller problem. The two halves want opposite things from a snapshot — the capture needs every read to agree with every other read, the limiter needs to see what the request ahead of it just committed — so they are now two transactions: a read-only **repeatable read** capture whose first query is the subject read (nothing blocks ahead of it, so the snapshot is the moment this request looked), then a **read committed** write phase that takes the lock and sees the previous holder. The subject is not re-read there: visibility was true when the reporter looked, and a withdrawal since does not unmake what they saw. Still not `select … for update` on the subject — letting a reporter block its author's edits is a worse thing to build into a reporting path.
- **A timestamp is not an identity, for the third time.** Reinstatement was guarded by `expectedSuspendedAt`, and `suspendAccount` overwrites `suspendedAt` with a `now` captured *before* it waits on the lock — so two suspensions serialized behind that lock can carry the same millisecond while differing in reason and in the decision recorded, and a page showing the first satisfied the predicate and lifted the second. The guard is now the `suspend` action's id, exactly as `unhideSubject` already used the hide's: it names the decision instead of the moment. A suspension with no recorded action behind it cannot be named, so the queue withholds Reinstate rather than sending an unguarded one.
- **The queue got slowest exactly when it mattered.** Describing each report on its own is four or five statements a row — about 500 for a full page — so the number of queries was the size of the backlog, and the tool for responding to abuse would time out at the moment abuse was arriving fastest. `listOpenReports` now bulk-loads: two rounds (the owners are not known until the subjects are read) and a fixed handful of statements whatever the page size, with `distinct on … order by seq desc` giving the same newest-decision-wins rule per subject that every single-subject read uses. `listSuspendedAccounts` takes the same treatment for the standing suspension ids it now has to return.
- **The counter sweep only ran when somebody used the AI.** `sweepExpiredCounters` was reachable from `reserveAiRequest` and nowhere else, so `/privacy`'s "rate-limit counters are dropped after a couple of days" held only while that feature was in use: a dormant account, or a quiet deployment, kept its rows indefinitely. This is the *same claim* WP-18 already caught once with no sweep behind it at all — found again one step milder, which is the argument for auditing a policy sentence against the code rather than against the last fix. `/api/cron/sweep` (daily, `CRON_SECRET`, 404 when the secret is unset — a route that runs deletes grants nobody by default) makes the schedule real, and the opportunistic call stays so a missed run degrades rather than stops. **And the first version of that route swept only the AI counters — the same mistake surviving its own fix.** `/privacy` names three things it prunes, and the other two had cleanup on their own feature's path in exactly the same way: a deployment with no native sign-ins kept `native_auth_codes`, which hold **encrypted session cookies**, and an account that stopped looking people up kept its phone probes. All three are swept on the schedule now. Reading the policy sentence and checking each clause against the code is the whole lesson, and it took three attempts to actually do it. **Needs `CRON_SECRET` set at deploy**, alongside the legal identity and `WHAIKEY_OPERATOR_IDS`.
- **Snapshotting the text was half of it: the report also has to record who to answer for it.** `deletePour` is a *hard* delete, so once the author removed the reported pour the queue lost the owner along with it — and the Suspend control with that. Deleting the evidence put the account itself out of moderation's reach while its report sat open. `reports.subject_owner_id` is recorded when the report is filed and the queue falls back to it, so the content going away stops being an answer for having posted it. Writing the test found the same escape one level deeper: `resolveOpenReport` verified a suspension's claim by asking the *live* subject who owned it, which a deleted pour cannot answer — so the report could not be closed by the very action that answered it, and would have sat past the SLA unless somebody dismissed it as unfounded. The recorded owner answers first now, with the live lookup as the fallback for reports filed before it existed.
- **The preview was not a preview, it was the only view.** 500 characters is a sensible length for something you can click through and a wrong one here: the queue has no expansion control and deliberately no link to the content, a comment runs to 1,000 characters and a tasting note to 11,000 — so abuse placed after the cutoff was unreadable to the one person who had to judge it. The cap is gone and the queue scrolls instead.
- **The idempotent hide had no button.** Several people reporting one comment is the ordinary case, and `hideSubject` was written for it: a hide over a hide records no second action and resolves the later report anyway, because that report genuinely is handled by the hide already in force. But the queue disabled Hide whenever `alreadyHidden` was true, which is exactly those rows — so the path existed, was commented, and was unreachable, and the remaining reports could only be closed by dismissing real complaints as unfounded. The control stays enabled and reads "Resolve as hidden".
- **Three foreign keys quietly revoked the deletion right.** `moderation_actions.actor_id`, `bottle_submissions.reviewed_by` and `bottles.submitted_by` referenced `user.id` with no delete policy, so Postgres's default `no action` made the row undeletable: an operator who touched the queue once, and — the worst of the three, which the review did not name — **any ordinary user who submitted a single bottle**. Every other user reference in the schema is `cascade` or `set null`; these three were the exceptions, and all three came from this lane. The escapes were to erase the audit history or to reassign a decision to somebody who did not make it, and an append-only trail survives neither, so all three become `set null`: the decision, its reason and its order keep, and the identity of a deleted account goes, which is what deletion is for. Null actor means "their account is gone", not "nobody acted". **And nullable columns needed the joins re-read** — both action lists `innerJoin`ed the actor, which would have dropped every action by a deleted operator out of the trail entirely, trading a delete the schema refused for history that deletes itself; worse on the standing-hides list, which carries the only control that lifts a hide, so its subject would have been stranded hidden with nothing able to unhide it. `bottles.submitted_by` clearing is safe because a verified bottle is catalog data other shelves point at, and `reviewed_by` clearing is safe because `state`, not the reviewer, is what says a submission is pending.
- **The audit trail is the current state, so it needed a real order.** Every "is this hidden right now" read is "the newest action on this subject", and the first version ordered by `created_at` with the row id as a tie-break — which *disambiguates* two rows without *ordering* them, because the id is a random UUID: two actions in the same millisecond resolved to whichever UUID sorted higher, and a request that sat behind the per-subject lock committed with a `now` captured before it waited, so a later decision could carry an earlier timestamp than the one it supersedes. Both are the same bug — a clock is not a sequence. `moderation_actions.seq` is a `bigserial` assigned inside the advisory lock, so the number a decision gets is the order it actually took effect in; all seven current-state reads order by it, and the standing-hides cursor is the bare sequence rather than a compound timestamp. The timestamps stay, because a human reading the trail wants to know *when* — they are just no longer what decides.
- **A profile cannot be hidden, and that is the honest answer rather than a missing feature.** Hiding uses each subject's own mechanism, and a profile's only mechanism is `socialEnabled` — which is a switch in the account's own settings. A hide there would last exactly as long as it took its owner to find the toggle they already have, while telling the operator they had acted; the queue would be full of decisions that silently didn't happen. So the action is refused at the schema, the button is not rendered for a profile subject, and suspension — the one an account cannot undo — is what the queue offers instead. For the same reason the queue no longer reads `socialEnabled` as "already handled": an account that stepped back of its own accord (US-11) is a privacy choice, not an actioned account.
- **Suspension is not `socialEnabled`.** The obvious implementation is to reuse the flag that already exists, and it is wrong: `socialEnabled` is a toggle in the user's own settings, so a suspended account could lift its own suspension. `suspendedAt` / `suspendedReason` are separate and only an operator writes them, `setSocialEnabled` refuses to turn social back **on** while suspended, and reinstating deliberately leaves the flag off — coming back is the user's choice to make again, not something moderation does to them.
- **Self-suspension is refused.** An operator locking the only operator account out of the queue is a one-keystroke outage with no recovery path short of a deploy.
- **The 72-hour target is measured, not asserted.** `REPORT_SLA_HOURS` is a constant, the queue sorts oldest-first and shows each report's age, and `countBreachedReports` is the number a status page can read. A target with nothing counting it is a sentence in a policy document.
- **The policy pages refuse to look finished.** A Terms and a Privacy Policy have to name a legal entity, a jurisdiction, a contact address and the date they take effect, and inventing plausible ones would be worse than leaving them blank — a policy that names the *wrong* entity is not a smaller problem than one that names none. They come from the environment (`src/lib/legal.ts`), and until all four are set both pages render a visible "this document is not finished" banner naming only the ones actually missing. (The date was optional as first shipped; see the two entries above for why that was wrong and what it broke.) That banner **is** the store-readiness check.
- **Feedback works signed out.** The people most able to tell you the app is broken are the ones who could not get into it. `POST /api/feedback` takes an anonymous body with an optional contact address; a support channel that requires a session cannot hear about a sign-in bug. The signed-out throttle is keyed on the forwarded address rather than being one allowance shared by everybody — a global counter would turn the one event this channel exists for, many people reporting one outage, into a silent drop after the fifth. It reads at `/admin/feedback`, outstanding first, each row markable handled: a list nobody can mark off is this lane's own mistake one level down.
- **Catalog review is the second queue, and it is not the same job.** `/admin/submissions` finishes WP-16: promote (the bottle becomes `verified` and its parked barcode becomes a `bottle_upcs` mapping, in one transaction — a barcode published before a human looked would let one submission answer everybody's scan), decline, or mark a duplicate of a bottle that is already public. Its record lives on the submission row rather than in `moderation_actions`: that table's subjects are the social ones, and widening it to carry catalog decisions would make both harder to read. Declining **deletes nothing** — the bottle stays `user_submitted`, so it keeps working on its submitter's shelf and in their journal; what is withheld is the shared catalog and the passport. The state predicate on the update is the concurrency control, so a second operator on the same row changes nothing and is told so.
- **Writing the Privacy Policy found a claim nothing enforced.** "Rate-limit counters are dropped after a couple of days" was in PLAN §9.2 and went into the policy text — and `ai_rate_limits` had no sweep at all, so every counter row (a user id and a timestamp) was kept forever. A policy claim nothing enforces is worse than no claim, so `sweepExpiredCounters` now drops rows whose window closed more than 48 hours ago, at most once per process per hour, outside the reservation transaction so a failed sweep cannot fail the request it rode in on. This is the useful part of writing the document down: it is an audit of what the code actually does, and it only works if you check.
- **A required reason nobody can read is not a reason.** Declining demands one, which meant the submitter needed somewhere to read it — `submission-status.tsx` on the bottle's own page, scoped to the submitter, saying waiting / declined-with-the-words-as-written / here-is-the-one-we-had. An approved submission says nothing at all: being in the catalog is the outcome.

Two things this closes that WP-16 and WP-17 left hanging: submissions have somewhere to be promoted from (WP-16's "no operator UI yet"), and `/terms`, `/privacy` and `/support` are ungated paths in `src/lib/age-gate.ts` — a gate that hides the privacy policy from someone deciding whether to answer it is the gate arguing against itself.

**Left open by WP-18.** Reviewer access (PLAN-C10) is an **owner decision**, not a task: the three viable shapes are recorded in `docs/APP_STORE_SETUP.md` §6.4 and PLAN.md §12, and the document now says no store record may be opened until one is chosen. Account deletion and export (SEC-M5) are still unbuilt, so the Privacy Policy describes the deletion path as a support request rather than a button — which is true today and should stop being true. **Merging** a duplicate is not built either: re-pointing a submitter's shelf rows and pours at the canonical bottle is a data migration, not a moderation action, so today a duplicate is recorded and the submitter keeps their own row. There is no settings screen yet (Lane B), so the policy and support links live in the footers of `/sharing`, `/responsible` and `/sign-in`.

**Status (WP-20).** Three small things, one of which is the only lever this architecture has.

- **`/api/native/manifest`** is the version floor the shell reads at boot. It matters because the app loads the deployed site: that is why a UI change ships without store review, and equally why a bad deploy reaches every installed app at once with nothing to roll back. Raising `WHAIKEY_MIN_SHELL_VERSION` above every released build parks the app behind an update screen — that is the kill switch. It **fails open**: an unreachable or unparseable manifest leaves the app running, because a version check that locks people out when the network hiccups is a worse outage than the one it prevents. A floor that fails to parse falls back to no floor *and logs loudly*, since a kill switch that silently isn't one is the same problem restated.
- **The push-token rule** (SEC-M6) needed the reasoning corrected, not just the code. The old comment said a token identifies a device rather than a person, which is true and beside the point: the token is the only credential in play and it is exactly the thing that leaks. It now stays with the account that registered it until that account releases it or stops refreshing it for a week — the legitimate hand-me-down goes through one of those two doors. **Both doors had to be built**: `disablePush` had no callers, so sign-out never released a token (`signOutCompletely` is now the one way out), and nothing re-registered an active device, so every row aged into "abandoned" after a week and the original attack came back a week late. The shell now refreshes an already-granted registration on launch and resume, without ever prompting.
- **`allowBackup=false`** (SEC-L2) rather than `dataExtractionRules` filtering: the app's data is all server-side, so there is nothing to back up and nothing to keep configuring correctly.

**Left open by WP-20.** The version check runs inside the React tree the deploy just sent, so it runs after that tree has mounted — the splash is held until it settles and the gate paints above everything, but a sibling effect calling a plugin the installed binary lacks has already run. Closing that needs the check to move into the **native launcher**, before the WebView is pointed at `server.url`. That is an architecture change to `docs/NATIVE_APP.md` §2.2's option C, not a patch, and it is recorded there rather than half-built here: today's floor is a UI gate, not a boot gate.

## Appendix A — what is done well (keep it that way)

1. **Concurrency discipline in the social layer**: per-user `pg_advisory_xact_lock('social-reset:…')` serialises every exposure-raising write against the privacy reset; `graph-pair:` locks order block-vs-follow; the re-share path is a textbook conditional update + re-read.
2. **Authorization**: one seam, verified handler by handler; no IDOR; ownership in the SQL predicate; uniform-response discipline against oracles; exemplary phone discovery.
3. **Rate limiting** is DB-backed and atomic across serverless instances.
4. **`claimWork`'s lock-free queue** is correct and explained.
5. **AI is genuinely optional**: every AI route 503s cleanly, `recommend.ts` is pure of AI, and the manual loop never blocks.
6. **Guardrails enforced in code**, not just documented.
7. **Migrations are clean** and in sync; backfills are idempotent by construction.
8. **CI** is thorough: typecheck, lint, 1,288 tests, build, Capacitor validation, Android compile per PR, iOS on main, functional and visual e2e in a pinned container.
9. **Hygiene**: zero `@ts-ignore`, zero TODO/FIXME/HACK, five justified lint suppressions, pinned fonts with the reason documented.
10. **The native seam holds**: nothing under `src/app` or `src/components` imports `@capacitor/*` directly; every capability has a web fallback.
11. **Three screens prove the team can hit the target composition**: Learn hub, Compare, Note discussion. The polish pass is bringing the other screens up to that bar, not inventing a new one.
